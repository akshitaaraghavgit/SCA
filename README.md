# MODULE 0: INTRODUCTION TO SIDE-CHANNEL ANALYSIS

## 1. What is Side-Channel Analysis (SCA)?

Side-Channel Analysis is a security analysis technique in which an attacker obtains information about a system by observing its physical or operational behaviour rather than directly accessing its protected data.

Normally, a computer is designed to protect information through:
- Encryption
- Authentication
- Access control
- Memory protection
- Secure execution

However, even when the actual data is protected, the way a computer processes that data can reveal information.

For example, consider a program that processes a secret encryption key.

The attacker may not be able to read the key directly, but might observe:

- How long the program takes to execute.
- How much power the processor consumes.
- Electromagnetic signals produced during computation.
- Changes in CPU cache behaviour.

These observations can reveal information about the secret.

This is the fundamental idea behind Side-Channel Analysis.

## 2. Major Types of Side Channels

| Side Channel | What the Attacker Observes |
|---|---|
| Timing Analysis | Execution time |
| Power Analysis | Electrical power consumption |
| Electromagnetic Analysis | Electromagnetic emissions |
| Acoustic Analysis | Sound generated by hardware |
| Cache Side Channel | CPU cache access patterns and timing |

Our primary focus is Cache Side-Channel Analysis.

# MODULE 1: THE HARDWARE REALITY
## How CPUs Handle Memory

Before understanding cache attacks, we must understand why CPU caches exist.

## 1. Why Do We Need a Cache?

A CPU can execute instructions extremely quickly.

However, fetching data from main memory (RAM) is comparatively slow.

Imagine a CPU performing millions or billions of operations while constantly waiting for RAM.

This creates a performance problem.

The solution is CPU caching.

A cache is a small, extremely fast memory located close to or inside the processor.

It temporarily stores copies of frequently or recently accessed data so that the CPU can retrieve them faster.

### Memory Hierarchy

A typical memory hierarchy looks like this:

CPU Registers
     |
     v
L1 Cache
     |
     v
L2 Cache
     |
     v
L3 Cache
     |
     v
Main Memory (RAM)
     |
     v
SSD / HDD

As we move downward:

- Storage capacity generally increases.
- Access latency generally increases.
- Cost per bit generally decreases.

### Different Cache Levels

**L1 Cache**

- Closest cache to the execution core.
- Extremely fast.
- Usually very small.
- Commonly divided into instruction cache (L1I) and data cache (L1D).

**L2 Cache**

- Larger than L1.
- Usually slower than L1.
- May be private to an individual core.

**L3 Cache**

- Usually larger than L1 and L2.
- Typically slower than L2.
- Often shared among multiple CPU cores.

The exact arrangement depends on the processor architecture.

## 2. What Happens When a CPU Requests Data?

Suppose a program requests a particular memory location.

The processor checks the cache hierarchy.

There are two important situations.

### Cache Hit

The requested data is already present in the cache.

Therefore, the CPU retrieves it quickly.

### Cache Miss

The requested data is not present in the relevant cache.

The processor must obtain it from a lower level of the memory hierarchy.

This takes additional time.

The fundamental relationship is:

Cache Hit = Faster Access

Cache Miss = Slower Access

This difference in access time becomes extremely important in cache side-channel attacks.

## 3. What Is a Cache Line?

A cache does not normally transfer individual bytes between memory and cache.

It transfers blocks of data called cache lines.

A cache line is a fixed-size block of contiguous memory.

A common cache-line size is 64 bytes, although this depends on the processor.

For example:

Suppose the cache line begins at address 0x1000.

It may contain:

0x1000 - 0x103F

That represents 64 bytes.

If the CPU accesses one byte within this region, the entire cache line may be brought into the cache.

Why does this matter?

Because an attacker may not need to know the exact byte accessed.

Observing which cache line was accessed can provide useful information.

# MODULE 2: ANATOMY OF A CPU CACHE

Understanding cache organisation is essential for understanding Prime + Probe.

## 1. Cache Organisation

A cache is commonly organised using:

- Cache Lines
- Cache Sets
- Cache Ways

### Cache Sets

A cache is divided into groups called sets.

Each memory block maps to a particular cache set.

### Cache Ways

Each set contains a fixed number of slots called ways.

For example:

A 4-way set-associative cache has four possible cache-line positions in every set.

If the CPU needs to store a new line in a full set, one of the existing lines may need to be evicted.

### Example

Imagine a cache with:

- 64 sets
- 4 ways per set
- 64-byte cache lines

Its total capacity is:

64 × 4 × 64 = 16,384 bytes

Therefore, the cache capacity is 16 KB.

## 2. Direct-Mapped Cache

In a direct-mapped cache, each memory block can occupy only one specific cache location.

Advantages:
- Simple organisation.
- Fast lookup.
- Low hardware complexity.

Disadvantage:
- More conflict misses when multiple memory blocks map to the same location.

## 3. Fully Associative Cache

In a fully associative cache, a memory block can occupy any available cache line.

Advantages:
- Maximum placement flexibility.
- Fewer conflict misses.

Disadvantages:
- More complex hardware.
- More expensive lookup mechanisms.

## 4. Set-Associative Cache

This combines the two approaches.

A memory block maps to one set but can occupy any way within that set.

This is a common cache organisation.

## 5. Why Does Cache Organisation Matter for Security?

Consider two processes running on the same processor.

They might not have access to each other's memory.

However, they may interact with the same physical cache.

If one process changes the state of a cache set, another process may observe the resulting timing difference.

This is the foundation of Prime + Probe.

The important distinction:

Memory isolation does not automatically mean microarchitectural isolation.

# MODULE 3: THE SHARED DESK ANALOGY

## What Is a Cache Side Channel?

Imagine two employees sharing an office.

There is one common desk.

Employee A places some documents on the desk.

Later, Employee B enters the room.

Employee B cannot open Employee A's locked cabinet.

However, Employee B can observe which documents are already present on the shared desk.

From this observation, Employee B may infer what Employee A was working on.

Now translate this into computer architecture.

| Real-World Analogy | Computer Architecture |
|---|---|
| Shared desk | CPU Cache |
| Documents | Cache Lines |
| Employee A | Victim Program |
| Employee B | Attacker Program |
| Documents placed on desk | Memory loaded into cache |
| Observing desk contents | Measuring cache behaviour |
| Inferring previous activity | Recovering secret-dependent information |

The attacker does not necessarily access the victim's protected memory.

Instead, the attacker observes changes in a shared hardware resource.

This is called a side channel.

## 1. Why Is This a Security Problem?

Suppose a victim program processes an encryption key.

Depending on the key, it accesses different memory locations.

Those memory accesses affect cache behaviour.

An attacker measures the resulting timing differences.

After collecting enough observations, the attacker may infer information about the key.

The attacker is not directly reading the encryption key.

The attacker is analysing the consequences of computations involving the key.

That distinction is extremely important.

# MODULE 4: THE FOUR-STEP PROCESS OF A CACHE ATTACK

Most cache attacks can be understood through four fundamental stages.

## STEP 1: Preparation

The attacker prepares the cache or identifies memory locations that will be monitored.

Depending on the attack technique, this may involve:

- Flushing selected cache lines.
- Loading selected memory addresses.
- Identifying cache sets.
- Preparing a timing measurement mechanism.

## STEP 2: Victim Execution

The victim program performs its normal computation.

For example:

- Encrypting a message.
- Processing authentication information.
- Performing cryptographic operations.
- Accessing secret-dependent memory locations.

These operations influence the CPU cache.

## STEP 3: Observation

The attacker measures the consequences of the victim's execution.

Possible observations include:

- Cache hit or miss.
- Memory access latency.
- Evicted cache lines.
- Changes in access timing.

## STEP 4: Analysis

The attacker collects multiple observations and analyses them.

Statistical analysis may help identify patterns.

Those patterns may reveal information about:

- Secret-dependent memory accesses.
- Cryptographic operations.
- Key-dependent branches.
- Victim execution behaviour.

### Complete Attack Flow

Attacker Preparation
        |
        v
Victim Executes
        |
        v
Cache State Changes
        |
        v
Attacker Measures
        |
        v
Timing Analysis
        |
        v
Possible Secret Information Leakage

Remember:

A single timing measurement rarely proves anything.

Cache attacks generally require repeated measurements, careful experimental control, and statistical analysis.

# MODULE 5: THE ATTACKER'S SUPERPOWER
## Hardware Instructions Used in Cache Attacks

Some processor instructions make cache observation and manipulation easier.

Understanding these instructions helps explain how practical cache attacks work.

The following examples primarily concern x86 processors.

They are not universally available on ARM or RISC-V processors.

## 1. CLFLUSH

CLFLUSH stands for Cache Line Flush.

It invalidates the cache line associated with a specified memory address from the relevant cache-coherence domain.

In simple terms:

It removes the selected cache line from the cache hierarchy according to the instruction's architectural guarantees.

Why is it useful?

An attacker can flush a cache line and later measure whether it was accessed again.

If the victim accesses the corresponding memory location, that line may become cached again.

This is useful in Flush + Reload.

Important:

CLFLUSH is an x86 instruction, not a universal CPU instruction.

## 2. RDTSC

RDTSC stands for Read Time-Stamp Counter.

It reads the processor's timestamp counter.

An attacker can use it to estimate how many timestamp-counter ticks occur between two events.

For example:

Start Timer
    |
    v
Access Memory
    |
    v
Read Timer Again
    |
    v
Calculate Elapsed Ticks

The measured time helps distinguish faster and slower memory accesses.

Important:

RDTSC does not automatically provide perfectly ordered measurements.

Instruction ordering, processor behaviour, virtualization and scheduling can affect results.

More careful measurement techniques may use LFENCE or RDTSCP where appropriate.

## 3. MFENCE

MFENCE stands for Memory Fence.

It provides ordering guarantees for memory operations.

It is useful when constructing controlled measurement sequences.

## 4. RDTSCP

RDTSCP reads the timestamp counter and also provides additional ordering guarantees.

It is often used in timing experiments.

However, correct ordering still requires understanding the surrounding instruction sequence.

## 5. Why Are These Instructions Important?

These instructions provide two important capabilities:

CLFLUSH:
Influence cache state.

RDTSC / RDTSCP:
Measure elapsed time.

Together, they help researchers investigate cache behaviour.

# MODULE 6: FLUSH + RELOAD
## Theory and Working

Flush + Reload is a cache side-channel technique.

It is particularly important because it can provide precise information about accesses to shared memory.

## 1. The Basic Idea

Suppose two processes share the same physical memory page.

For example:

- A victim program uses a shared library.
- An attacker maps the same shared physical memory.

Although the processes have separate virtual address spaces, the corresponding memory may refer to the same physical page.

This creates an opportunity for cache observation.

## 2. How Does Flush + Reload Work?

It has three primary operations.

### Operation 1: Flush

The attacker flushes a selected cache line.

This creates a starting condition in which the line is not expected to remain cached.

### Operation 2: Wait for Victim

The attacker allows the victim program to execute.

If the victim accesses the shared cache line, that line may become cached again.

If the victim does not access it, the line may remain absent from the cache.

### Operation 3: Reload

The attacker accesses the same memory location.

The attacker measures how long this access takes.

If the access is fast, it suggests that the line was cached.

If it is slow, it suggests that the line was not cached or had to be fetched from a lower level.

        ATTACKER
            |
            v
      Flush Cache Line
            |
            v
       Wait for Victim
            |
            |
            v
        VICTIM
            |
            v
   Accesses Shared Memory?
            |
            v
      Cache State Changes
            |
            v
        ATTACKER
            |
            v
       Reload Memory
            |
            v
      Measure Access Time
            |
            v
       Infer Cache Access

## 4. Why Is Shared Memory Important?

Flush + Reload relies on the attacker and victim referring to the same physical cache line.

This is possible even when their virtual addresses differ.

Examples of possible shared-memory situations include:

- Shared libraries.
- Memory-mapped shared files.
- Other shared physical pages.

Without a suitable shared cache line, traditional Flush + Reload cannot perform its normal observation mechanism.

## 5. What Does the Timing Tell Us?

Suppose an attacker measures:

Observation A: 45 timestamp ticks

Observation B: 210 timestamp ticks

Observation A is significantly faster.

It may indicate that the cache line was already present.

Observation B may indicate that the line was fetched from a slower cache or memory level.

These are illustrative values, not universal thresholds.

The attacker repeats the experiment to distinguish meaningful patterns from noise.

## 6. Simplified Conceptual Pseudocode

The following pseudocode describes the observation process.

It is an educational representation, not a complete attack implementation.

    for each measurement:

        flush(target_cache_line)

        wait_for_victim_execution()

        start_time = read_timestamp()

        access(target_cache_line)

        end_time = read_timestamp()

        elapsed_time = end_time - start_time

        record(elapsed_time)

    analyse_measurements()

The important concept is:

Flush -> Victim Execution -> Reload -> Measure.

## 7. Limitations of Flush + Reload

- Requires suitable shared physical memory.
- Requires access to an appropriate cache-flush mechanism.
- Timing measurements are affected by noise.
- Scheduling and interrupts can interfere.
- Modern hardware and software mitigations can make exploitation harder.

# MODULE 7: PRIME + PROBE
## When Attackers Don't Share Memory

Prime + Probe is another major cache side-channel technique.

Its most important distinction from Flush + Reload is that it does not require the attacker and victim to share the same physical memory line.

## 1. Why Do We Need Prime + Probe?

Consider this situation:

An attacker wants to observe a victim process.

However, the victim and attacker do not share memory.

The attacker cannot simply flush and reload the victim's memory address.

Does this mean the attacker cannot observe cache activity?

No.

The attacker may exploit the organisation of cache sets.

## 2. The Basic Idea

Remember:

A set-associative cache contains multiple cache sets.

Multiple memory addresses can map to the same cache set.

If the attacker accesses enough carefully selected addresses mapping to one set, those accesses occupy the available ways.

This is called Priming.

When the victim subsequently accesses data mapping to the same cache set, some attacker cache lines may be evicted.

The attacker then accesses their own addresses again.

This is called Probing.

By measuring the access time, the attacker estimates whether eviction occurred.

## 3. The Three Stages

### STAGE 1: PRIME

The attacker accesses a collection of addresses that map to a selected cache set.

The objective is to occupy the cache ways with attacker-controlled data.

Imagine a four-way cache set:

Way 0 -> Attacker Address A

Way 1 -> Attacker Address B

Way 2 -> Attacker Address C

Way 3 -> Attacker Address D

The attacker has populated the set.

### STAGE 2: VICTIM EXECUTION

The victim executes normally.

Suppose the victim accesses an address that maps to the same cache set.

The cache may need to evict one of the attacker's lines to make room.

For example:

Way 0 -> Victim Address

Way 1 -> Attacker Address B

Way 2 -> Attacker Address C

Way 3 -> Attacker Address D

Attacker Address A may have been evicted.

The attacker does not directly observe the victim's memory.

The attacker observes the consequences of cache replacement.

### STAGE 3: PROBE

The attacker accesses the original addresses again.

If an address is still cached, its access may be fast.

If it was evicted, its access may be slower.

By measuring these differences, the attacker estimates which cache sets were affected.

## 5. Why Is Prime + Probe Different?

| Feature | Flush + Reload | Prime + Probe |
|---|---|---|
| Shared physical memory | Required for the standard technique | Not required |
| Flush instruction | Normally required | Not required |
| Observation method | Reload timing | Probe timing |
| Main observation | Shared cache-line access | Cache-set contention |
| Granularity | Often cache-line level | Generally cache-set level |
| Difficulty | Depends heavily on shared-memory access | Cache mapping and noise can make it difficult |

## 6. Limitations of Prime + Probe

- Cache-set identification can be difficult.
- Modern cache indexing may be complex.
- Cache replacement policies affect observations.
- Other processes can create interference.
- Measurements require statistical analysis.
- It may provide less precise information than Flush + Reload.

# MODULE 8: PRIME + PROBE
## Code Blueprint and Logical Implementation

This module explains the internal logic of Prime + Probe.

The objective is to understand the algorithm rather than build an exploit against a real application.

## 1. What Does the Code Need?

A conceptual Prime + Probe experiment requires:

1. A collection of memory addresses.
2. Addresses mapping to the same cache set.
3. A mechanism to access those addresses.
4. A timing mechanism.
5. A way to record and compare measurements.

## 2. Conceptual Algorithm

    initialize eviction_addresses

    while experiment_is_running:

        # PRIME

        for address in eviction_addresses:

            access(address)

        # VICTIM EXECUTION

        allow_victim_to_execute()

        # PROBE

        total_time = 0

        for address in eviction_addresses:

            start = read_timestamp()

            access(address)

            stop = read_timestamp()

            elapsed = stop - start

            record(elapsed)

            total_time += elapsed

        # ANALYSIS

        analyse(total_time)

The pseudocode illustrates the stages without assuming a particular CPU cache geometry or replacement policy.

## 3. Understanding the Variables

**eviction_addresses**

The addresses selected by the attacker.

They are intended to map to the same cache set.

**access(address)**

An operation that reads from the specified address.

**read_timestamp()**

A timing operation used to measure elapsed time.

**total_time**

The accumulated access time during probing.

**analyse()**

The analysis stage used to estimate whether cache eviction occurred.

## 4. Why Do We Need Multiple Measurements?

A single slow memory access does not necessarily prove that the victim accessed the same cache set.

Possible reasons include:

- CPU interrupts.
- Context switches.
- Cache replacement.
- Memory hierarchy effects.
- Other processes.
- Measurement overhead.

Therefore, multiple observations are collected.

Repeated measurements make it possible to identify statistically meaningful patterns.

## 5. Expected Behaviour

Scenario A:

Attacker primes the cache.

Victim does not access the monitored set.

Attacker probes.

Expected result: Many attacker addresses remain cached.

Scenario B:

Attacker primes the cache.

Victim accesses addresses mapping to the monitored set.

Attacker probes.

Expected result: Some attacker addresses may have been evicted.

The timing difference helps distinguish the two situations.

Important:

Actual behaviour depends on cache architecture, associativity, replacement policy and system activity.

# MODULE 9: THE THREE MAJOR ATTACK TECHNIQUES

Cache side-channel research includes several techniques.

Three important examples are:

## 1. Flush + Reload

Mechanism:

Flush -> Victim Access -> Reload -> Measure

Requirements:

- Shared physical cache line.
- Cache-flush capability.
- Timing measurement.

Main observation:

Whether the victim accessed a particular shared cache line.

## 2. Prime + Probe

Mechanism:

Prime -> Victim Execution -> Probe -> Measure

Requirements:

- Knowledge or discovery of cache-set mappings.
- Eviction-set construction.
- Timing measurements.

Main observation:

Whether victim activity caused contention in a monitored cache set.

## 3. Evict + Reload

Mechanism:

Evict -> Victim Execution -> Reload -> Measure

Instead of explicitly flushing a cache line using a cache-flush instruction, the attacker attempts to evict it by accessing other memory addresses.

If the victim subsequently accesses the monitored line, the attacker may observe a faster reload.

This technique can be useful when explicit cache-flush instructions are unavailable or unsuitable.

## 4. Comparison

| Technique | Initial Operation | Observation |
|---|---|---|
| Flush + Reload | Flush target line | Reload latency |
| Prime + Probe | Fill selected cache set | Probe latency |
| Evict + Reload | Evict target line through contention | Reload latency |

# MODULE 10: WHAT DO ATTACKERS ACTUALLY STEAL?
## Real-World Targets

An important question:

If attackers cannot directly read protected memory, what information can they actually recover?

The answer depends on the victim program and the information leaked through its memory-access patterns.

## 1. Cryptographic Keys

Cryptographic algorithms use secret keys during encryption and decryption.

Some implementations perform memory accesses that depend on secret information.

If an attacker can correlate cache behaviour with those accesses, the attacker may infer information about the key.

Examples of research areas:

- AES cache attacks.
- Table-based cryptographic implementations.
- Cache attacks against cryptographic libraries.

Important:

Not every AES implementation is vulnerable.

Constant-time implementations are designed to avoid secret-dependent timing and memory-access behaviour.

## 2. Browser Information

Browsers execute complex applications containing JavaScript, cryptographic operations and shared resources.

Research has demonstrated that microarchitectural side channels can reveal information about browser activity under certain conditions.

Potential targets include:

- Secret-dependent operations.
- Sensitive application activity.
- Information processed by vulnerable browser components.

Modern browsers use multiple security protections to make such attacks more difficult.

## 3. Password-Related Information

Cache side channels may help reveal information about password-processing operations.

However, recovering an actual password is not automatic.

The attacker needs a suitable leakage source and a way to interpret the observations.

## 4. Cloud Computing

Cloud platforms may run workloads belonging to different customers on shared physical hardware.

This creates an important security consideration.

Different virtual machines may have separate memory spaces but still interact through shared microarchitectural resources.

Researchers have investigated cache side channels in:

- Multi-tenant cloud environments.
- Virtual machines.
- Shared processors.
- Trusted execution environments.

## 5. Trusted Execution Environments

Trusted execution environments are designed to protect sensitive computations.

However, protecting memory contents does not necessarily eliminate leakage through microarchitectural behaviour.

Cache side-channel research has investigated attacks against systems such as Intel SGX.

The lesson:

A protected execution environment must consider not only direct memory access but also information leaked through hardware behaviour.

# MODULE 11: EXISTING SOLUTIONS
## How Do We Stop Cache Side-Channel Attacks?

There is no single defence that completely eliminates every cache side channel.

Different attacks require different countermeasures.

The most important defensive approaches are explained below.

## 1. Constant-Time Programming

This is one of the most important software-level defences.

A constant-time implementation aims to ensure that execution behaviour does not depend on secret information.

For example, consider a cryptographic program.

Unsafe conceptual implementation:

    if secret_bit == 1:

        access(table[1])

    else:

        access(table[0])

The memory access depends on the secret bit.

This can create an observable side channel.

A constant-time approach aims to avoid secret-dependent branches and memory accesses.

The objective:

Secret changes should not produce distinguishable execution behaviour through the relevant observable channels.

Important:

Constant-time programming is not simply making every operation take exactly the same number of CPU cycles.

It requires careful control of secret-dependent branches, memory accesses and other observable behaviour.

## 2. Cache Partitioning

Cache partitioning divides cache resources between different processes or security domains.

For example:

Process A -> Cache Partition A

Process B -> Cache Partition B

This reduces the possibility of one process interfering with another process's assigned cache resources.

One example of hardware support is Intel Cache Allocation Technology (CAT).

However, partitioning does not automatically eliminate all side channels.

Its effectiveness depends on the resources being partitioned and the attack being considered.

## 3. Cache Flushing

A system may flush selected cache contents during security-sensitive transitions.

For example:

Before switching between security domains:

Flush selected cache state.

This can reduce information leakage from previous activity.

However:

- Flushing can introduce performance overhead.
- It may not clear every relevant microarchitectural state.
- It is not a universal solution.

## 4. Cache Randomisation

Cache randomisation attempts to make the relationship between memory addresses and cache locations less predictable.

If an attacker cannot easily determine which addresses map to the same cache set, constructing reliable eviction sets becomes more difficult.

Randomisation can increase attack complexity.

However, it does not guarantee complete protection.

## 5. Hardware Isolation

Hardware can isolate resources between security domains.

Possible approaches include:

- Cache partitioning.
- Resource allocation controls.
- Improved cache replacement policies.
- Stronger isolation between execution environments.

The objective is to reduce unintended interference between processes.

## 6. Reduce Information Leakage

Software developers should avoid:

- Secret-dependent memory indexing.
- Secret-dependent branches.
- Data-dependent lookup tables in sensitive cryptographic code.
- Unnecessary sharing of sensitive memory.

This is especially important when implementing cryptographic algorithms.

# MODULE 12: ADVANCED COUNTERMEASURES
## How Modern Engineering Fights Back

This module goes beyond basic mitigation and examines broader defensive strategies.

## 1. Intel Cache Allocation Technology (CAT)

CAT provides hardware mechanisms for controlling cache allocation.

It allows the operating system or hypervisor to influence which portions of the last-level cache can be used by particular workloads.

Why is this useful?

Two workloads can be assigned different cache resources.

This reduces cache contention between them.

Security benefit:

It can reduce certain cross-workload cache side channels.

Limitation:

It does not eliminate every shared microarchitectural resource or every possible side channel.

## 2. Intel Total Memory Encryption and AMD Secure Memory Encryption

Memory encryption technologies protect data stored in physical memory.

Examples include:

- Intel TME.
- AMD SME.

These technologies help protect data confidentiality against certain physical-memory threats.

However, an important distinction must be understood:

Memory encryption does not automatically prevent cache side-channel attacks.

Why?

Cache attacks may observe access patterns and timing without directly reading encrypted memory contents.

Therefore, memory encryption and cache-side-channel mitigation address different security problems.

## 3. Speculative Execution Mitigations

Modern processors execute instructions speculatively to improve performance.

Under certain conditions, speculative execution can influence microarchitectural state even when architectural execution later discards the speculative results.

Spectre is an important example of a vulnerability class involving speculative execution and side channels.

Mitigations may include:

- Speculation barriers.
- Restricting speculative behaviour.
- Compiler-based protections.
- Hardware changes.
- Operating-system isolation.

These protections address speculative-execution-related information leakage.

They should not be confused with complete protection against all conventional cache attacks.

## 4. Constant-Time Cryptographic Libraries

Cryptographic libraries are increasingly designed to minimise secret-dependent execution behaviour.

Examples include cryptographic implementations using:

- Constant-time arithmetic.
- Hardware cryptographic instructions.
- Secret-independent memory access.
- Carefully controlled branching.

Hardware acceleration can help reduce some software leakage opportunities, although the implementation must still be evaluated for side channels.

## 5. Operating System and Hypervisor Isolation

Operating systems and hypervisors can reduce opportunities for attackers to observe other workloads.

Possible approaches:

- Isolating security-sensitive processes.
- Restricting untrusted co-location.
- Managing CPU scheduling.
- Applying cache controls.
- Using stronger virtual-machine isolation.

This is particularly important in cloud computing.

## 6. Performance Monitoring and Detection

Researchers also investigate detecting abnormal cache behaviour.

Possible signals include:

- Unusual cache miss rates.
- Excessive cache contention.
- Suspicious access patterns.
- Repeated high-resolution timing activity.

However, detecting cache attacks is difficult because legitimate applications also produce complex cache activity.

Detection systems must balance security, performance and false positives.

# MODULE 13: HOW ALL THE DEFENCES FIT TOGETHER

A useful way to understand countermeasures is to divide them into three levels.

## LEVEL 1: SOFTWARE DEFENCES

Examples:

- Constant-time programming.
- Avoiding secret-dependent memory access.
- Secure cryptographic libraries.
- Reducing unnecessary shared memory.

Main objective:

Prevent secret information from influencing observable execution behaviour.

## LEVEL 2: OPERATING SYSTEM DEFENCES

Examples:

# MODULE 15: IMPORTANT TECHNICAL TERMINOLOGY

Use this section as a quick revision dictionary.

### Side Channel
An indirect information source created by observable system behaviour.

### Cache
Small, fast memory that stores copies of frequently accessed data.

### Cache Line
A fixed-size block of memory transferred between memory hierarchy levels.

### Cache Hit
Requested data is available in the relevant cache.

### Cache Miss
Requested data is not available at the relevant cache level.

### Cache Set
A group of cache lines into which particular memory blocks map.

### Cache Way
One possible cache-line position within a cache set.

### Cache Eviction
Removal of a cache line to make room for another line.

### Cache Contention
Competition between memory accesses for limited cache resources.

### Cache Latency
Time required to access data through the cache hierarchy.

### Flush
An operation that invalidates a cache line.

### Reload
Accessing a memory address again, often to measure whether it is cached.

### Prime
Filling selected cache sets with attacker-controlled cache lines.

### Probe
Measuring access latency to determine whether cache lines remain present.

### Shared Memory
Memory accessible through mappings used by multiple processes.

### Physical Address
The address used to identify a location in physical memory.

### Virtual Address
An address used by a process and translated by the memory management system.

### Constant-Time Programming
Writing software so that relevant observable execution behaviour does not depend on secret data.

### Cache Partitioning
Dividing cache resources between workloads or security domains.

### Microarchitecture
The internal implementation of a processor.

### Speculative Execution
Executing instructions before knowing whether they are ultimately required.

### Timing Analysis
Inferring information by measuring execution or memory-access time.

### Eviction Set
A collection of memory addresses that can collectively evict a target cache line or contend for a particular cache set.

# MODULE 16: FINAL REVISION
## Understanding the Complete Picture

This is the most important section to revisit before explaining cache side-channel attacks to someone else.

## 1. Why Do Cache Attacks Exist?

CPU caches are designed to improve performance.

They store recently accessed memory to avoid slower memory accesses.

However, cache behaviour depends on program activity.

This means that one process may indirectly observe changes caused by another process.

## 2. What Is the Main Security Weakness?

The problem is not necessarily that the attacker can access protected memory.

The problem is that shared microarchitectural resources can reveal information about another process.

Memory isolation does not guarantee complete microarchitectural isolation.

## 3. What Does an Attacker Observe?

The attacker observes:

- Cache hits.
- Cache misses.
- Access latency.
- Cache evictions.
- Cache-set contention.

These observations may reveal secret-dependent behaviour.

## 4. What Is Flush + Reload?

The attacker:

1. Flushes a shared cache line.
2. Waits for the victim.
3. Reloads the same memory location.
4. Measures access time.

The attacker infers whether the victim accessed the shared line.

## 5. What Is Prime + Probe?

The attacker:

1. Fills selected cache sets.
2. Allows the victim to execute.
3. Accesses the attacker's addresses again.
4. Measures access time.

The attacker infers whether victim activity caused cache eviction.

## 6. What Is the Difference?

Flush + Reload observes a shared cache line.

Prime + Probe observes cache-set contention.

That is the most important distinction between these two techniques.

## 7. What Information Can Leak?

Depending on the victim and the leakage mechanism:

- Cryptographic information.
- Secret-dependent memory access patterns.
- Information about application activity.
- Information processed in shared computing environments.

The attack does not automatically recover passwords or encryption keys.

Successful exploitation requires an appropriate leakage source and sufficient observations.

## 8. How Do We Defend Against These Attacks?

The main approaches are:

1. Constant-time programming.
2. Cache partitioning.
3. Cache flushing.
4. Cache randomisation.
5. Hardware isolation.
6. Operating-system isolation.
7. Secure cryptographic implementations.

No single approach is sufficient against every possible cache side channel.
